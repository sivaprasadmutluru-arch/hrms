# Roles & Permission System — Current vs Best Approach

---

## Side-by-Side Comparison

| # | Aspect | Current (Django / Horilla) | Best Approach (Spring Boot RBAC) |
|---|--------|---------------------------|----------------------------------|
| 1 | **Role storage** | No roles table. Uses `is_superuser` and `is_staff` boolean flags on `auth_user` table | Dedicated `roles` table with named roles stored as rows |
| 2 | **Role names** | Only one named group in DB: `"Company Admin"` (hardcoded string in payroll sidebar code) | `SUPER_ADMIN`, `COMPANY_ADMIN`, `HR_MANAGER`, `MANAGER`, `EMPLOYEE` — stored in DB, not hardcoded |
| 3 | **Permission storage** | Auto-generated strings per model (`attendance.view_attendance`, `employee.change_ownprofile`) in `auth_permission` table | Explicit `permissions` table with meaningful names (`attendance:validate`, `leave:approve`) |
| 4 | **Role ↔ Permission link** | No clean link — permissions assigned directly to users or groups | `role_permissions` junction table — each role has a defined set of permissions |
| 5 | **User ↔ Role link** | `auth_user_groups` junction (but barely used — only 1 group exists) | `user_roles` junction table — a user can have multiple roles across companies |
| 6 | **Permission checks** | `@permission_required("module.action_model")` decorator scattered across every view function | `@PreAuthorize("hasAuthority('module:action')")` on service/controller methods — centralized |
| 7 | **Superuser logic** | `if request.user.is_superuser:` inline checks repeated in every module's sidebar and views | `SUPER_ADMIN` role with a wildcard authority — handled once in `SecurityConfig` |
| 8 | **Manager access** | Custom `@manager_can_enter`, `@owner_can_enter` decorators — checks reporting manager FK relationship inline | `MANAGER` role + `@PreAuthorize` with Spring SpEL expressions checking ownership/hierarchy |
| 9 | **Module-level access** | Each module has its own `sidebar.py` with handwritten permission logic duplicated per module | One `PermissionEvaluator` bean evaluates all access rules centrally |
| 10 | **Multi-approval logic** | `MultipleApprovalCondition` model — managers checked inline inside leave views | Configurable approval workflow service — rules stored in DB, not in code |
| 11 | **Recruitment manager** | Checked by querying `Recruitment.recruitment_managers` M2M inside `@is_recruitment_manager` decorator | Functional role stored as an assignment record — evaluated by generic authorization service |
| 12 | **Company-scoped roles** | No company-scoped roles — `is_superuser` is platform-wide, regular users get permissions platform-wide | Roles are scoped per company — a user can be `HR_MANAGER` in Company A and `EMPLOYEE` in Company B |
| 13 | **Adding a new role** | Requires code changes: new group name string, new decorator, sidebar logic update | Insert a new row in `roles` table + assign permissions — zero code change |
| 14 | **Adding a new permission** | Auto-generated by Django when model is created — no control over granularity | Explicitly defined in `permissions` table — full control over what actions exist |
| 15 | **Checking own data** | `@owner_can_enter` decorator — checks if `employee_id == request.user.employee` inline | `@PostAuthorize("returnObject.employeeId == authentication.principal.id")` — Spring Security standard |
| 16 | **Inverted logic** | Leave sidebar uses `NOT is_superuser AND NOT has_perm` (hiding admin features) — confusing and error-prone | Boolean flag `isAdminOnly` on permission record — evaluated cleanly in one place |
| 17 | **Auditing who has what role** | Have to query `auth_user_groups` + `auth_user_user_permissions` separately — no single view | Single query on `user_roles` + `role_permissions` — easy to audit |
| 18 | **Role hierarchy** | None — flat permission assignment | Role hierarchy supported: `SUPER_ADMIN > COMPANY_ADMIN > HR_MANAGER > MANAGER > EMPLOYEE` |
| 19 | **API security** | Session-based with `@login_required` + `@permission_required` decorators | JWT token carries authorities — `SecurityFilterChain` validates on every request |
| 20 | **Scalability** | Works for small teams — becomes spaghetti as modules grow (350KB of views with scattered permission checks) | Scales cleanly — permissions enforced at service layer, independent of how many modules are added |

## DB Schema Comparison

### Current (Django)
```
auth_user
  id | username | email | is_superuser | is_staff | is_active
  ----------------------------------------------------------------
  1  | admin    | ...   | true         | true     | true
  2  | john     | ...   | false        | false    | true

auth_group
  id | name
  ---------
  1  | Company Admin          ← only one row ever created

auth_permission
  id | codename                    | content_type_id
  --------------------------------------------------
  1  | view_attendance             | attendance
  2  | change_validateattendance   | attendance
  3  | view_employee               | employee
  ... (auto-generated, 4 per model × 60+ models = 240+ rows)

auth_user_groups          ← barely populated
  user_id | group_id

auth_user_user_permissions   ← where all permissions actually live
  user_id | permission_id
```

### Best Approach (Spring Boot RBAC)
```
roles
  id | name           | description
  -----------------------------------
  1  | SUPER_ADMIN    | Full platform access
  2  | COMPANY_ADMIN  | Full access within company
  3  | HR_MANAGER     | HR operations within company
  4  | MANAGER        | Team/department management
  5  | EMPLOYEE       | Own data only

permissions
  id | module      | action            | description
  ---------------------------------------------------
  1  | employee    | view              | View employees
  2  | employee    | create            | Add employees
  3  | employee    | edit              | Edit employees
  4  | employee    | delete            | Delete employees
  5  | attendance  | view              | View attendance
  6  | attendance  | validate          | Validate attendance
  7  | attendance  | approve_overtime  | Approve overtime
  8  | leave       | view              | View leave requests
  9  | leave       | approve           | Approve leave
  10 | leave       | allocate          | Allocate leave days
  11 | payroll     | view              | View payslips
  12 | payroll     | generate          | Generate payslips
  13 | payroll     | confirm           | Confirm payslips
  14 | recruitment | view              | View recruitment
  15 | recruitment | manage            | Manage pipeline
  16 | asset       | view              | View assets
  17 | asset       | assign            | Assign assets
  ... (explicit, meaningful, ~50 total)

role_permissions
  role_id | permission_id
  -------------------------
  1 (SUPER_ADMIN)   | ALL
  2 (COMPANY_ADMIN) | ALL except platform settings
  3 (HR_MANAGER)    | employee:*, attendance:*, leave:*, payroll:*, recruitment:*
  4 (MANAGER)       | employee:view, attendance:validate, leave:approve, ...
  5 (EMPLOYEE)      | own data only

users
  id | username | email | is_active | ...

user_roles  ← scoped per company
  user_id | role_id | company_id
  --------------------------------
  2 (john) | 3 (HR_MANAGER)  | 1 (Acme HQ)
  2 (john) | 5 (EMPLOYEE)    | 2 (Acme Dubai)   ← different role in different company
```

## Decision Summary

| Factor | Current Django | Best Approach | Winner |
|--------|---------------|---------------|--------|
| Role management | Code changes required | DB-driven, zero code change | **Best** |
| Company-scoped roles | Not supported | Fully supported | **Best** |
| Permission granularity | 240+ auto-generated, uncontrolled | ~50 explicit, meaningful | **Best** |
| Permission checking | Scattered across 350KB of views | Centralized Spring Security | **Best** |
| Multi-company user | One global role only | Different role per company | **Best** |
| Setup complexity | Simple (Django handles it) | More upfront setup | **Current** |
| Learning curve | Low (Django built-in) | Medium (Spring Security) | **Current** |
| Auditability | Hard — split across 4 tables | Easy — 2 tables | **Best** |
| Scalability | Breaks down as codebase grows | Scales cleanly | **Best** |

**Verdict: Use the Best Approach for the Spring Boot rebuild.**
The Django approach was convenient for a Python/Django project because the framework auto-generated permissions.
In Spring Boot, we don't have that auto-generation — so doing RBAC properly costs almost the same effort
but gives a far cleaner and more maintainable system long-term.
